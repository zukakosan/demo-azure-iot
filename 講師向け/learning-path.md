# 講師向けキャッチアップパス

## 目的

この資料は、講師が Azure IoT Hub の講義とデモを担当するための準備順序をまとめたものです。
操作手順を覚えるだけでなく、各操作について「誰が、どこへ、何を送り、どの結果を確認するのか」を説明できる状態を目指します。

## キャッチアップ完了の目安

- Azure IoT ソリューション全体の中で、IoT Hub の役割を説明できる
- デバイスの登録、認証、接続、テレメトリ送信の流れを説明できる
- D2C、Direct Method、Device Twin、C2D メッセージの用途を区別できる
- メッセージルーティングと、受信ツールによる確認の違いを説明できる
- DPS が自動化する登録・割り当てと、デバイス側で事前に必要な準備を区別できる
- デモ構成と本番構成の違い、今回の講義で扱わない範囲を説明できる

## 準備の順番

| Step | 学ぶこと | 実際に確認すること | 完了条件 |
| --- | --- | --- | --- |
| 1 | 既存デモの構成 | デバイスの接続、テレメトリ送信、クラウド側での受信を一通り実行し、画面表示とコードを対応させる | どのプログラムが、どの認証情報を使い、どこへ何を送っているか説明できる |
| 2 | Direct Method による即時操作 | クラウド側から開始・停止を呼び出し、デバイス側のハンドラー、応答、送信状態の変化を追う | 要求と応答の流れ、およびデバイスが未接続の場合の扱いを説明できる |
| 3 | Device Twin による設定同期 | Desired Properties で送信間隔を変更し、デバイスへの反映と Reported Properties の更新を確認する | Direct Method による操作と、Twin による状態・設定同期の違いを説明できる |
| 4 | メッセージの配送 | 条件と配送先を設定して結果を比較する。環境制約で保存確認を保留した場合は未検証として記録する | 受信・配送・保存の違いと、配送先を用途・ネットワーク要件から選ぶ理由を説明できる |
| 5 | DPS による初回接続の自動化 | DPS と IoT Hub をリンクし、個別登録した学習用デバイスの割り当て・接続・D2C・無効化を確認する | 手動登録との違い、DPS の役割、事前準備と再登録防止の必要性を説明できる |
| 6 | 本番利用への移行 | 切断・再送、資格情報、監視、容量、費用、接続方式、多数台の管理を確認する | 「デモで動く」状態から「運用できる」状態にするための確認事項を挙げられる |
| 7 | 講義全体の組み立て | 各操作を Azure IoT の全体図に戻し、導入からまとめまで通して説明する | 今回扱う範囲と対象外の範囲を明示し、各章を一つのユースケースでつなげられる |

## 各 Step の進め方

### Step 1: 既存デモの構成を理解する

1. IoT Hub、デバイス ID、デバイスアプリ、受信ツールの役割を図にする
2. デバイスアプリを起動し、接続ログを確認する
3. テレメトリを送信し、クラウド側で同じメッセージを確認する
4. 接続文字列を使う主体と、データの向きを確認する

この段階では、コードを変更するよりも、ログとコードの対応を追うことを優先します。

#### 到達目標

- IoT Hub、デバイス ID、デバイスアプリ、受信ツールの役割と通信方向を説明できる。
- デバイス側の送信ログとクラウド側の受信結果を対応させ、送信した温度・湿度を確認できる。
- デバイスの資格情報と、クラウド側の操作・読み取りに使う資格情報を区別できる。

### Step 2: Direct Method の流れを追う

1. クラウド側から送信開始の Method を呼び出す
2. デバイス側で呼び出される処理と、返却するステータス・ペイロードを確認する
3. 送信停止の Method を呼び出し、テレメトリが止まることを確認する
4. Direct Method が即時応答を前提とする操作に向く理由を整理する

#### 到達目標

- クラウドの要求、デバイスのハンドラー実行、応答返却の流れを説明できる。
- 応答のステータス・ペイロードと、実際のテレメトリ送信状態を別々に確認できる。
- 未接続や応答タイムアウト時の扱いを説明し、「応答を確認できない」を「未実行」と決めつけずに再試行を検討できる。

### Step 3: Device Twin の設定同期を確認する

1. Desired Properties に送信間隔を設定する
2. デバイスが変更を受け取り、送信間隔へ反映する処理を確認する
3. 適用結果を Reported Properties へ書き戻す
4. Direct Method、Device Twin、C2D メッセージの使い分けを表で説明できるようにする
    - C2D メッセージはデバイスごとのキューに保持され、有効期限内に再接続すれば受信できる。無期限の保持ではない（[C2D メッセージのライフサイクル](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-messages-c2d)）。

#### 到達目標

- Desired は期待する設定、Reported はデバイスが報告した状態であり、自動的に同じ値になるものではないと説明できる。
- 送信間隔の変更について、Desired の更新、デバイスでの適用、Reported の報告を追跡できる。
- 即時の操作要求、継続的な設定同期、期限付きの個別通知を例に、Direct Method・Device Twin・C2D を選び分けられる。

### Step 4: メッセージルーティングを理解する

1. テレメトリのプロパティまたは本文を使った条件を一つ決める
2. ルートと配送先を設定する
3. 条件に一致するメッセージと一致しないメッセージを送り、結果を比較する
4. IoT Hub は長期保存先ではなく、後続サービスへデータを渡す入口であることを確認する

学習環境では組織のネットワーク制約により、保存先への実際の保存確認は保留しています。概念の理解と動作検証は区別し、保存確認を完了済みとせずに Step 5 へ進みます。本番化時の接続方式は Step 6 で検討します。

#### 到達目標

- データソース・条件・エンドポイントを区別し、`true` と温度条件がそれぞれ何を対象にするか説明できる。
- 組み込みエンドポイントでの受信と後続サービスでの保存を区別し、フォールバックが配送先障害の代替保存ではないことを説明できる。
- 保存・検索・分析・業務処理という目的に加え、ネットワーク要件を踏まえて配送先を選ぶ観点を挙げられる。
- 組み込みエンドポイントの保持期間には限りがあることを説明し、実際に検証できた範囲と未検証の範囲を示せる。

### Step 5: DPS による初回接続を一通り確認する

手動登録したデバイスと、DPS（Device Provisioning Service）経由で登録したデバイスを比較します。講師自身の実践として取り組み、受講者向けの講義では役割と流れの紹介に留めます。

1. DPS を作成し、既存の IoT Hub をリンクする。
2. 学習用デバイスの個別登録を作成する。最初は対称キー方式を使い、登録・割り当ての流れに集中する。
3. デバイス側に初期アプリ、DPS の接続情報（ID スコープなど）、登録 ID とデバイス固有の資格情報を用意する。接続先 IoT Hub のデバイス接続文字列を手で指定する構成と比較する。
4. デバイスから DPS に登録要求を送り、DPS の登録結果と、割り当て先 IoT Hub のデバイス登録を確認する。
5. 割り当て結果を使って IoT Hub に直接接続し、D2C テレメトリを送信して受信結果を確認する。
6. 可能なら2台目でも試し、共通コードとデバイス固有の ID・資格情報を分離する意味を確認する。
7. 学習用デバイスの利用終了を想定し、DPS の個別登録と IoT Hub のデバイスを無効化する。DPS で新たな登録要求が拒否されることと、IoT Hub で新たな接続が拒否されることを分けて確認する。

登録・割り当ては DPS が自動化しますが、端末側の初期アプリや資格情報の準備までは自動化しません。初回の登録後、通常の通信は DPS を経由せず IoT Hub と直接行います（[DPS の動作と事前準備](https://learn.microsoft.com/ja-jp/azure/iot-dps/about-iot-dps#how-device-provisioning-service-works)）。

無効化・削除は DPS と IoT Hub の両方で扱います。DPS 側だけでは既存の IoT Hub 登録が削除されず、IoT Hub 側だけでは DPS を通じて再登録される可能性があります。登録グループを使う場合は、個別登録を削除するだけで再登録防止になるとは限らないため、認証方式と登録階層に応じた手順が必要です（[プロビジョニング解除](https://learn.microsoft.com/ja-jp/azure/iot-dps/how-to-unprovision-devices)）。

#### 到達目標

- 手動登録と比較し、DPS が自動化するデバイス登録・接続先の割り当てを説明できる。
- DPS の登録結果、IoT Hub 側の登録、D2C の受信を対応させ、初回接続の流れを確認できる。
- DPS は通常通信の中継先ではなく、登録後はデバイスが IoT Hub に直接接続すると説明できる。
- 多数台でも共通アプリとデバイス固有の資格情報は別に準備し、DPS がソフトウェア配布を代行するわけではないと説明できる。
- 利用終了時に、IoT Hub での接続停止と DPS での再登録防止をセットで扱う理由を説明できる。

X.509 の登録グループ、複数 Hub への割り当て、再プロビジョニングは発展課題に回します。対称キーの個別登録を体験したことだけで、多数台の本番認証方式を決めたとは扱いません（[DPS の登録と機能](https://learn.microsoft.com/ja-jp/azure/iot-dps/about-iot-dps)、[X.509 登録グループによる複数デバイスの登録](https://learn.microsoft.com/ja-jp/azure/iot-dps/tutorial-custom-hsm-enrollment-group-x509)）。

### Step 6: 本番化の論点を整理する

次の問いに対して、デモ構成の制約と本番で必要になる検討を説明できるようにします。

- デバイスが切断した場合、未送信データと再送をどう扱うか
- 資格情報をどう保護し、更新し、失効させるか
- データが届かない場合、どのログやメトリックを確認するか
- 台数、送信頻度、メッセージサイズから容量と費用をどう見積もるか
- 配送先への接続は、承認されたネットワーク例外でよいか、Private Endpoint 経由が必須か
- Step 5 の DPS を踏まえ、多数台の初期アプリ配置・資格情報の準備・登録をどう分担するか
- 設定変更、ソフトウェア更新、故障交換、廃棄をどう管理し、対象群へ段階的に適用するか

#### 到達目標

- デモにはない再接続・再送・重複対策・監視の必要性を説明し、許容停止時間やデータ損失量を検討できる。
- デバイスの資格情報と配送先の認証・認可・ネットワーク到達性を区別し、組織ポリシーに適合する接続方式の判断材料を挙げられる。
- 台数・送信頻度・メッセージサイズから、容量と費用を見積もるための前提を整理できる。
- 登録、設定管理、ソフトウェア更新、監視、無効化・削除をライフサイクルとして整理し、DPS だけでは完結しないことを説明できる。
- 一括変更を送った事実と各デバイスでの適用成功を区別し、段階展開・結果確認・失敗時の対応を検討できる。

多数台の管理では、Twin のタグなどで対象を整理し、自動デバイス構成による Desired の適用と Reported による結果確認を検討します。一括の Direct Method 呼び出しには Jobs、ソフトウェア更新には端末側の更新機構を含む別の設計が必要です（[デバイス構成のベストプラクティス](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-configuration-best-practices)、[Jobs による一括操作](https://learn.microsoft.com/ja-jp/azure/iot-hub/schedule-jobs-cli)、[Device Update の更新フロー](https://learn.microsoft.com/ja-jp/azure/iot-hub-device-update/understand-device-update#device-update-workflows)）。

### Step 7: 講義として通して確認する

1. 工場の温度センサーという共通ユースケースで全章をつなぐ
2. 全体像、接続、送信、制御、状態同期、配送、本番化の順に説明する
3. デモを含めてリハーサルし、操作待ち時間と失敗時の代替画面を確認する
4. まとめで、各機能をどの場面で選ぶか問いかける

#### 到達目標

- 温度センサーのユースケースを使い、各章の機能と責任範囲を一つの流れで説明できる。
- 講師自身の実践範囲と受講者に扱う範囲を区別し、DPS の詳細実践を講義の必須デモに増やさず紹介できる。
- 90分版・120分版それぞれの省略箇所、操作待ち時間、失敗時の代替説明を判断できる。
- 実施済みの検証と未実施の検証を明示し、受信者が機能を選び分けられる問いで講義を締めくくれる。

## 最終チェック

- [ ] デモ用の IoT Hub とデバイス ID が準備されている
- [ ] デバイスアプリの起動方法と必要な設定値を把握している
- [ ] D2C テレメトリをクラウド側で確認できる
- [ ] Direct Method による開始・停止を実演できる
- [ ] Device Twin による送信間隔変更と適用結果を確認できる
- [ ] ルーティングの理解と、保存確認の実施・未実施を区別して説明できる
- [ ] DPS で学習用デバイスを登録・割り当てし、IoT Hub への接続と D2C の受信を確認した
- [ ] DPS が自動化する範囲と、初期アプリ・資格情報の事前準備を説明できる
- [ ] DPS の登録無効化と IoT Hub のデバイス無効化をそれぞれ確認した
- [ ] 多数台の登録・設定・更新・監視・廃棄に必要な役割分担を説明できる
- [ ] デモ失敗時に見せるログまたは画面を用意している
- [ ] 90 分版と 120 分版の省略箇所を把握している
- [ ] 終了後に削除するリソースを把握している
