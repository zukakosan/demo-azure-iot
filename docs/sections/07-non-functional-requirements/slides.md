## 07-01 非機能要件は本番リスクから優先する

### このページの役割

本章で用いる「必須・推奨・発展」は Microsoft の公式分類ではなく、ワークショップで本番リスクを整理するための判断ガイドだと明示する。

### 投影本文

**非機能要件は、未定義のまま本番へ進んだときの影響から優先する。**

| 重要度 | 本章での意味 | 判断の目安 |
| --- | --- | --- |
| 必須 | 本番移行前に決定・検証する | 侵害、データ損失、長時間停止、復旧不能につながる |
| 推奨 | 初期リリース時点で方針を決める | 検知、調査、スケール、コスト管理に影響する |
| 発展 | 規模拡大に備えて計画する | 複数拠点、標準化、継続的な改善に効く |

- Azure Well-Architected Framework の5つの柱を使い、信頼性・セキュリティ・コスト・運用・性能の偏りを確認する。[1]
- 重要度はサービス機能の優劣ではなく、今回の業務で許容できない影響から決める。

**「高可用」「安全」で終わらせず、目標値、判断基準、責任者、確認方法まで定義する。**

### 図の構成

- 左から「必須」「推奨」「発展」を段差状に配置し、各段に判断の目安を1行で示す。
- 右下に Well-Architected Framework の5観点を小さな円環で配置する。公式の優先順位に見えないよう、5観点は同じ大きさにする。

### 出典

[1] https://learn.microsoft.com/ja-jp/azure/well-architected/what-is-well-architected-framework

### 講師ノート

- 目安: 1分。最初に「必須・推奨・発展は公式ラベルではない」と明言する。
- 例として「月間可用性99.9%」だけでなく、停止時の判断者と復旧手順が必要だと説明する。
- 次への接続: 「抽象的な要望を、測定できる要件へ変えます」。
- 出典: https://learn.microsoft.com/ja-jp/azure/well-architected/what-is-well-architected-framework

## 07-02 本番前に測定可能な目標を決める

### このページの役割

本番化で最初に合意する観点を一覧化し、要件を Azure の設定項目だけでなく、システム全体の目標と責任分界へ落とす。

### 投影本文

**サービスを選ぶ前に、業務影響から測定可能な目標と責任者を決める。**

| 観点 | 要件として決める例 | 設計・運用へ反映する項目 |
| --- | --- | --- |
| セキュリティ | 侵害時に対象デバイスを何分で無効化するか | 認証方式、失効手順、RBAC、ネットワーク制御 |
| 信頼性・データ | 許容停止時間と許容データ損失量 | SLO、RTO、RPO、バッファ、再送、保持・削除 |
| 性能・拡張性 | 台数、送信頻度、サイズ、ピーク遅延 | SKU、ユニット数、クォータ、負荷試験 |
| 運用・コスト | 検知時間、復旧時間、月額上限 | メトリック、アラート、Runbook、予算 |

**IoT Hub の SLA を、そのままシステム全体の SLO にはしない。デバイス、ネットワーク、配送先、業務処理までを対象にする。** [1]

### 図の構成

- 中央に4行の対応表を置き、左から「観点」「測る目標」「設計・運用」の流れを矢印で示す。
- 下部に「デバイス → ネットワーク → IoT Hub → 配送先 → 業務処理」の細い全体経路を置き、SLO の対象範囲を示す。

### 出典

[1] https://learn.microsoft.com/ja-jp/azure/reliability/reliability-iot-hub

### 講師ノート

- 目安: 1分30秒。表の全項目を読み上げず、「要件」と「Azure の設定」を混同しない点を強調する。
- SLO、RTO、RPO は説明用語として短く補足する。RTO は復旧までの目標時間、RPO は許容するデータ損失の時点である。
- 数値は個別の業務で決める。この資料では正解値を提示しない。
- 次への接続: 「最初の必須項目として、デバイスの本人確認をライフサイクルで考えます」。
- 出典: https://learn.microsoft.com/ja-jp/azure/reliability/reliability-iot-hub

## 07-03 デバイス資格情報を製造から廃棄まで管理する

### このページの役割

デバイス認証を接続時の設定だけで終わらせず、資格情報を扱う主体と、更新・侵害・廃棄までを設計対象にする。

### 投影本文

**デバイスごとに一意の ID と資格情報を割り当て、共有資格情報を使い回さない。** [1]

| 段階 | 決めること |
| --- | --- |
| 製造・初期設定 | 誰が資格情報を発行し、デバイスの安全な領域へ格納するか |
| 配送・設置 | 資格情報と機器の対応をどう確認し、漏えいをどう防ぐか |
| 運用・更新 | 証明書やキーをどう更新・ローテーションし、失敗時にどう戻すか |
| 侵害・交換・廃棄 | 対象デバイスだけを無効化し、再登録をどう防ぐか |

- 認証方式は、脅威モデル、デバイス性能、製造工程、更新可能性から選ぶ。
- 本番では X.509 証明書や TPM など、秘密鍵をハードウェアで保護できる方式を検討する。[2]
- ファームウェア更新では、署名検証、セキュアブート、失敗時のロールバックも設計する。

**認証方式の選択と、資格情報を運び続ける運用手順はセットで決める。**

### 図の構成

- 「製造 → 配送・設置 → 運用・更新 → 交換・廃棄」を循環するライフサイクル図にする。
- 中央に「デバイス固有 ID・資格情報」を置き、各段階の担当者を記入できる空欄ラベルとして表現する。

### 出典

[1] https://learn.microsoft.com/ja-jp/azure/iot-hub/secure-azure-iot-hub

[2] https://learn.microsoft.com/ja-jp/azure/iot-dps/concepts-service#attestation-mechanism

### 講師ノート

- 目安: 1分30秒。X.509 や TPM を一律の正解とはせず、製造工程と更新可能性まで含めて選ぶと説明する。
- DPS の Enrollment を削除しても、既存の IoT Hub のデバイス ID は自動削除されない。廃棄時は両側を確認する。
- 次への接続: 「クラウド側も、接続する主体ごとに許可を分けます」。
- 出典: https://learn.microsoft.com/ja-jp/azure/iot-hub/secure-azure-iot-hub
- 出典: https://learn.microsoft.com/ja-jp/azure/iot-dps/concepts-service#attestation-mechanism

## 07-04 配送先の権限とネットワーク到達性を分ける

### このページの役割

第5章の Storage 配送を例に、デバイス、Portal 操作者、IoT Hub のマネージド ID は別の主体であり、認証・認可・ネットワークを個別に満たす必要があると示す。

### 投影本文

**デバイスが IoT Hub に送信できても、IoT Hub が Storage に書き込めるとは限らない。**

| 確認する層 | Storage 配送で確認すること |
| --- | --- |
| 認証 | エンドポイントで使用するマネージド ID はどれか |
| 認可 | その ID に Storage Blob Data Contributor を、対象コンテナーを含む範囲で付与したか [1] |
| ネットワーク | Storage 側が IoT Hub からの送信接続を許可する構成か [2] |

- Portal 操作者の権限と、IoT Hub が配送に使う権限は別に確認する。
- マネージド ID にロールを付与しても、ネットワーク制限は解除されない。
- IoT Hub の Private Endpoint は IoT Hub に接続する側の入口であり、Storage への直接配送を顧客 VNet 経由に変える機能ではない。[2]

**権限エラーに見えても、主体、ロール、対象範囲、ネットワークの順に切り分ける。**

### 図の構成

- 左に IoT Hub、右に Storage を置き、間に「認証」「認可」「ネットワーク」の3つのゲートを並べる。
- 上部に Portal 操作者を別の主体として配置し、IoT Hub のマネージド ID と混同しないよう線を分ける。

### 出典

[1] https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-managed-identity#configure-message-routing-with-managed-identities

[2] https://learn.microsoft.com/ja-jp/azure/iot-hub/virtual-network-support#egress-connectivity-from-iot-hub-to-other-azure-resources

### 講師ノート

- 目安: 1分30秒。ネットワーク制限下の対応可否は、配送先と使用する ID の種類ごとに公式仕様を確認する。
- Private Endpoint 経由だけが許可される場合は、VNet 内の受信アプリが IoT Hub の組み込みエンドポイントから読み、Storage へ書く構成を候補にする。その場合はチェックポイント、再試行、監視、実行基盤の運用も必要になる。
- 接続のために「すべてのネットワークを許可」を既定の解決策にしない。
- 次への接続: 「次に、デバイスを1台ずつ手動登録しない仕組みを見ます」。
- 出典: https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-managed-identity#configure-message-routing-with-managed-identities
- 出典: https://learn.microsoft.com/ja-jp/azure/iot-hub/virtual-network-support#egress-connectivity-from-iot-hub-to-other-azure-resources

## 07-05 DPS で初回登録と接続先割り当てを自動化する

### このページの役割

Device Provisioning Service（DPS）が何をするサービスかと、手動登録に対するメリットを、独立して説明する。初回登録後の通常通信は DPS を経由しないことも示す。

### 投影本文

**DPS は、デバイスを認証して接続先 IoT Hub を割り当てる、初回登録の自動化サービス。** [1]

手動で1台ずつ IoT Hub にデバイスを登録する代わりに、DPS が認証・登録・割り当てを自動化する。

**初回登録の流れ**

`デバイス → DPS で認証・Enrollment 照合・割り当て決定 → IoT Hub へ登録 → 割り当て結果を受領 → IoT Hub へ直接接続`

**工場出荷時の初期設定（手動登録の代わりに用意するもの）**

- DPS の接続情報: ID スコープ、グローバル エンドポイント、登録 ID。特定の IoT Hub の接続文字列ではない。
- 資格情報: 認証方式に応じて X.509 証明書 / TPM / 対称キー。

**手動登録との違い（メリット）**

- 手動登録が不要: 工場出荷時の初期設定だけで、現地で自動的に接続できる。
- 接続先を固定しない: 出荷後に割り当て先 IoT Hub を決定・変更できる。
- 多数台・多拠点に強い: 複数 IoT Hub への割り当てを一元的に管理できる。
- 割り当ての自動化: 割り当てポリシーで負荷分散や地理的な割り当てができる。

**Enrollment は登録を許可するための事前設定で、IoT Hub のデバイス ID とは別。通常のテレメトリは DPS を経由しない。** [2]

### 図の構成

- 上段にデバイス・DPS・IoT Hub の初回登録フローを横一列で配置し、最後の「IoT Hub へ直接接続」を通常通信として区別する。
- 下段を左右2列にし、左は「工場出荷時の初期設定」として ① DPS の接続情報 と ② 資格情報 の2枚のカードを、右は手動登録との違い（メリット）の箇条書きを置く。
- 初期設定は「DPS の接続情報」と「資格情報」の2種類だと一目で分かるようにする。
- 図形、矢印、テキストは PowerPoint で編集可能にする。

### 出典

[1] https://learn.microsoft.com/ja-jp/azure/iot-dps/about-iot-dps#how-device-provisioning-service-works

[2] https://learn.microsoft.com/ja-jp/azure/iot-dps/concepts-service#enrollment

### 講師ノート

- 目安: 1分30秒。まず「DPS は初回登録を自動化するサービス」と一言で示し、続けて手動登録との違いを説明する。
- ゼロタッチに近い運用でも、工場出荷時の初期設定（資格情報と DPS の接続情報）は必要である。
- 登録の自動化だけで運用は完成しない。設定変更、更新、監視、交換、廃棄は次のスライド以降で扱う。
- 次への接続: 「では、DPS のどの登録方式を使うかを整理します」。
- 出典: https://learn.microsoft.com/ja-jp/azure/iot-dps/about-iot-dps#how-device-provisioning-service-works
- 出典: https://learn.microsoft.com/ja-jp/azure/iot-dps/concepts-service#enrollment

## 07-06 直接登録・個別登録・グループ登録を使い分ける

### このページの役割

DPS を使うと決めた後に、IoT Hub への直接登録と、DPS の個別登録・グループ登録をどう選ぶかを示す。

### 投影本文

**台数と接続先の要件から、IoT Hub への直接登録と DPS の登録方式を選ぶ。**

| 方式 | クラウド側の事前準備 | 向いている例 |
| --- | --- | --- |
| IoT Hub へ直接登録 | 接続先 Hub にデバイス ID を登録 | 少数台で接続先が固定される検証 |
| DPS の個別登録 | DPS にデバイスごとの Enrollment を作成 | 1台ずつ管理し、出荷先決定後に Hub を割り当てる |
| DPS のグループ登録 | 共通の認証方式に基づく Enrollment Group を作成 | 同じ管理単位に属する多数デバイスを登録する |

- 個別登録でも、デバイスの本人確認と接続先 IoT Hub の決定を分離できる。[1]
- グループ登録でも各デバイスの資格情報は必要で、全デバイスで同じ秘密情報を使い回す意味ではない。[2]
- DPS の設定を変えただけでは接続中のデバイスは移動せず、デバイスから再プロビジョニング要求が必要になる。[3]

**登録エントリの管理を集約することと、接続先をデバイスに固定しないことは、別々のメリットとして説明する。**

### 図の構成

- 3方式の比較表を上に置き、「事前準備」と「向いている例」を同じ列で対比する。
- 表の下に、上記3点を箇条書きで添える。

### 出典

[1] https://learn.microsoft.com/ja-jp/azure/iot-dps/concepts-service#enrollment

[2] https://learn.microsoft.com/ja-jp/azure/iot-dps/concepts-service#enrollment-group

[3] https://learn.microsoft.com/ja-jp/azure/iot-dps/concepts-device-reprovision#reprovisioning-policies

### 講師ノート

- 目安: 1分15秒。「DPS でも1台ずつ個別登録するなら、直接登録と何が違うか」を問いかける。
- 個別登録は Enrollment の件数を減らさないが、接続先 Hub をプロビジョニング時に割り当てられる。
- 「出荷先の顧客が決まってから Hub を割り当てたい」なら、個別登録でも DPS を使う意味がある。
- 次への接続: 「多数のデバイスを一度に登録するときの注意点を見ます」。
- 出典: https://learn.microsoft.com/ja-jp/azure/iot-dps/concepts-service#enrollment
- 出典: https://learn.microsoft.com/ja-jp/azure/iot-dps/concepts-service#enrollment-group
- 出典: https://learn.microsoft.com/ja-jp/azure/iot-dps/concepts-device-reprovision#reprovisioning-policies

## 07-07 大量オンボーディングは時間差登録と再試行で守る

### このページの役割

DPS を導入しても、全デバイスを同時に初回登録するとスロットリングが起き得ることを示し、登録バッチと再試行を設計対象にする。

### 投影本文

**大量デバイスを一斉に登録せず、DPS の制限と計画期間から登録バッチを分散する。** [1]

| 設計項目 | 決めること |
| --- | --- |
| 登録スケジュール | 工場、拠点、出荷ロットなどの単位で開始時刻をずらす |
| バッチサイズ | DPS の登録制限と、期間内に登録する総台数から決める |
| 一時エラー | `429` では `Retry-After` を優先し、即時再試行を避ける |
| 再試行間隔 | 指数バックオフとランダムなジッターで要求を分散する |
| 検証 | ピーク登録率、失敗率、完了時間を本番前に負荷試験する |

**再試行は成功率を上げる仕組みだが、全デバイスが同じ間隔で再試行すると負荷をさらに集中させる。** [1]

### 図の構成

- 上段に「一斉登録」の高い単一ピークと `429` を描く。
- 下段に「時間差登録」の複数バッチをタイムライン上へ均等に配置し、バックオフとジッターで再試行時刻が分散する様子を描く。
- 特定の登録数を固定値として図示せず、制限値に基づき決めることを注記する。

### 出典

[1] https://learn.microsoft.com/ja-jp/azure/iot-dps/concepts-deploy-at-scale

### 講師ノート

- 目安: 1分30秒。Learn の「1分あたり200台」は説明例であり、利用環境の固定上限として投影しない。最新の DPS クォータと制限を確認してバッチを決める。
- 電源投入、回線復旧、ファームウェア更新後にも接続集中が起きる。初回登録だけの問題ではない。
- SDK の既定再試行を使う場合も、対象エラー、最大回数、期限、`Retry-After` の扱いを確認する。
- 次への接続: 「再起動したデバイスが、毎回 DPS に戻る必要があるかを整理します」。
- 出典: https://learn.microsoft.com/ja-jp/azure/iot-dps/concepts-deploy-at-scale

## 07-08 再接続と再プロビジョニングを使い分ける

### このページの役割

一時切断後に同じ IoT Hub へ戻る再接続と、接続先割り当てをやり直す再プロビジョニングを区別する。不要な DPS 登録要求の集中を避ける判断を示す。

### 投影本文

**再起動や一時切断のたびに DPS へ戻らず、保存した割り当て情報で同じ IoT Hub への再接続を先に試す。** [1]

```text
割り当て済み Hub の情報があるか
  ├─ ない → DPS でプロビジョニング
  └─ ある → 同じ IoT Hub へ直接再接続
               ├─ 成功 → 通常通信を再開
               └─ 継続して失敗 → エラーと方針に基づき DPS で再プロビジョニング
```

| 処理 | 目的 | 代表的な場面 |
| --- | --- | --- |
| 再接続 | 以前に割り当てられた Hub へ戻る | 一時的な回線断、再起動、サービスの一時障害 |
| 再プロビジョニング | 接続先の割り当てを確認・変更する | Hub の移行、リージョン変更、工場出荷時リセット |

- `429` では `Retry-After`、`5xx` ではバックオフを使い、短時間の失敗だけで全台を DPS へ戻さない。[1]
- デバイスから再プロビジョニングを開始できる手段と、その実行条件を設計する。

**キャッシュできないデバイスは起動時に DPS を使うため、その再登録率も容量計画へ含める。** [1]

### 図の構成

- 投影本文のテキストフローを、判断ひし形と処理ボックスを使った編集可能なフローチャートにする。
- 「通常は同じ Hub へ直接再接続」を主経路として太くし、DPS は条件付きの分岐として描く。

### 出典

[1] https://learn.microsoft.com/ja-jp/azure/iot-dps/concepts-deploy-at-scale

### 講師ノート

- 目安: 2分。再接続は通信の復旧、再プロビジョニングは割り当ての再決定である。
- 公式記事では、`401`、`403`、`404` は完全な再登録、`5xx` はキャッシュ済み情報などを使った再試行という判断例を示している。実装では SDK の動作とシステムの移行方針を合わせて確認する。
- Hub が一時停止しているだけなのに全台が DPS へ戻ると、障害を増幅し得る。Learn では同じ Hub への直接接続を15～30分試す考え方も示している。
- 保存対象は平文の共有シークレットに限定しない。割り当て先ホスト名、Device ID、認証方式に応じた安全な資格情報の参照を扱う。
- 次への接続: 「この判断が機能しているか、容量と監視をシステム全体で確認します」。
- 出典: https://learn.microsoft.com/ja-jp/azure/iot-dps/concepts-deploy-at-scale

## 07-09 信頼性・容量・監視をエンドツーエンドで設計する

### このページの役割

可用性、容量、監視、コストを別々のチェック項目ではなく、デバイスから後続処理まで連続する運用設計としてまとめる。

### 投影本文

**IoT Hub が稼働しているかだけでなく、必要なデータが必要な時間内に業務処理まで届くかを監視する。**

| 観点 | 本番前に決めること |
| --- | --- |
| 切断・再送 | バックオフとジッター、デバイス側バッファ、重複判定、順序の扱い |
| 容量 | 台数、送信頻度、サイズ、ピーク係数、操作別スロットリング、配送先の処理能力 [1] |
| 監視 | 接続数、認証エラー、スロットリング、ルーティング失敗、データ未着、DPS の登録率 [2][3] |
| 対応 | 重要度、通知先、一次対応者、Runbook、復旧・フェールオーバー演習 |
| コスト | Hub ユニット、保存期間、ログ量、通信量、1台・1拠点当たりの目標原価 |

- 1つの IoT Hub の上限を超える規模では、複数 Hub への分割と DPS の割り当てを計画する。[1][3]
- Basic は主に D2C 向け。Device Twin、Direct Method、C2D を使う構成は Standard を選ぶ。[1]

**技術メトリックと「一定時間データが来ない」という業務視点のアラートを組み合わせる。**

### 図の構成

- 横方向に「デバイス → ネットワーク → DPS / IoT Hub → 配送先 → 業務処理」を配置する。
- 上段に容量・スロットリング、下段にメトリック・ログ・業務アラートを対応させる。
- 右端に Runbook と責任者を置き、監視が通知だけで終わらないことを示す。

### 出典

[1] https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-scaling

[2] https://learn.microsoft.com/ja-jp/azure/iot-hub/monitor-iot-hub

[3] https://learn.microsoft.com/ja-jp/azure/iot-dps/concepts-deploy-at-scale

### 講師ノート

- 目安: 1分30秒。数値上限を暗記させず、最新のクォータを確認し、しきい値と増強手順を事前に決めることを到達点にする。
- DPS は登録グループ別の登録台数や、一定期間の登録率を監視する。登録失敗と IoT Hub 接続失敗を同じ障害として集計しない。
- IoT Hub の接続成功だけでなく、Storage への保存や業務処理完了まで相関できるイベント ID と時刻を持たせる。
- コスト削減で送信頻度やログ保持を変える場合は、SLO、調査可能期間、データ品質への影響を記録する。
- 次への接続: 「実際の構成図を、サービス一覧ではなく責任分界として読みます」。
- 出典: https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-scaling
- 出典: https://learn.microsoft.com/ja-jp/azure/iot-hub/monitor-iot-hub
- 出典: https://learn.microsoft.com/ja-jp/azure/iot-dps/concepts-deploy-at-scale

## 07-10 ケーススタディから責任分界を読み解く

### このページの役割

複数サービスを組み合わせた実例を、本章の観点で読み解く。図を標準構成として模倣せず、分離単位、優先度、処理完了の責任を問う。

### 投影本文

**事例の構成をそのまま採用せず、自分の要件に照らして設計判断を読み解く。**

社内事例を簡略化した構成図を、編集可能な図形で示す。固有名詞は匿名化している。主フローは次のとおり。

`車両 → Protocol Gateway → ブランド別 IoT Hub（ブランドA / ブランドB） → Service Bus（High / Normal） → Telemetry processor → Extensions → External Systems`。ブランドB 側は Passthrough Processor を経由して外部システムへ渡す。

| 図から読み取る観点 | 自分のシステムで確認する問い |
| --- | --- |
| ブランド別の IoT Hub | 顧客・拠点・環境・データ所在地のどの単位で接続先と運用を分けるか |
| High／Normal の経路 | 優先度をどこで判定し、混雑時の処理時間をどう保証・監視するか |
| 後続処理と外部連携 | どこまで到達したら業務処理完了とし、誰が再処理・復旧を担うか |

**図だけでは、認証、ネットワーク、冗長化、再試行、重複対策、監視の実装状況は判断できない。**

### 図の構成

- 元資料のスクリーンショットは使わず、同じ構成を編集可能な PowerPoint 図形で再構成し、固有名詞は匿名化する。
- 左から「車両 → Protocol Gateway → ブランド別 IoT Hub」を配置し、ブランドA とブランドB を上下に分けて接続先の分離を示す。
- ブランドA 側は Service Bus（High / Normal の2つのキュー）→ Telemetry processor → Extensions → External Systems へ横一列で結ぶ。
- ブランドB 側は Passthrough Processor を経由して外部システムへ渡す下段の経路として描く。
- Azure サービスは青、外部システムは緑で塗り分け、凡例と「原図を簡略化」の注記を添える。上段のサービス有効化（キャッシュ・データベース・イベント配信）や分岐ロジックの吹き出しは省略する。
- 図の下に、接続先の分離・優先度別の処理・責任分界の3枚のカードを並べる。

参考（社内資料）: IoT Readiness Refresher 2025 - Day 01、スライド11 を基に簡略化して作図。固有名詞は匿名化し、元資料のスクリーンショットは掲載しない。

### 講師ノート

- 目安: 1分15秒。車両から Protocol Gateway、ブランド別 IoT Hub、Service Bus、Telemetry processor、Extensions、External Systems の順に追う。
- High／Normal という名称だけで優先処理が保証されるとは断定しない。キュー、コンシューマー、スケール、監視の実装が必要である。

## 07-11 本番移行判定チェックリスト

### このページの役割

本章の観点を、本番移行の可否を判断するチェックリストへまとめる。すべての項目を実装済みにするのではなく、少なくとも判断・責任者・検証状況が明確かを確認する。

### 投影本文

**必須項目が未定義なら、機能デモが成功していても本番移行のリスクは高い。**

| 重要度 | 本番移行前の確認 |
| --- | --- |
| 必須 | 脅威モデルとデータ分類をレビューした |
| 必須 | デバイス固有 ID、資格情報の更新・失効、交換・廃棄の手順と責任者を決めた |
| 必須 | 配送先の主体、権限、対象範囲、ネットワーク方式を承認済み構成で検証した |
| 必須 | エンドツーエンドの SLO、RTO、RPO と、再送・重複の扱いを合意した |
| 推奨 | 平常時、ピーク、登録・再接続集中を含む容量試験を実施した |
| 推奨 | DPS、IoT Hub、配送先、業務処理の監視、アラート、Runbook を動作確認した |
| 推奨 | 月額予算、データ・ログ保持、コストアラートを設定した |
| 発展 | Hub 分割、リージョン障害、復旧・フェールオーバーを演習した |

**確認すること: 目標値は測れるか。失敗時に誰が判断するか。実際の制約下で復旧まで試したか。**

### 図の構成

- 左端に重要度、中央にチェック項目、右端に「決定済み／検証済み／責任者」の3つの確認欄を置く。
- 必須4項目を上段にまとめ、推奨・発展と視覚的に区切る。色だけでなくラベルでも区別する。
- 下部に「次章: 全体像と使い分けを振り返る」を小さく配置する。

### 講師ノート

- 目安: 1分。全項目を読み上げず、必須項目に未定義があれば移行判定で明示的に扱うとまとめる。
- 「検討した」だけでなく、目標値、責任者、検証結果が残っているかを確認する。
- 発展項目も、対象規模や業務影響によっては初回リリースから必須になり得る。
- 次章では IoT Hub の役割、通信方式、ルーティング、本番化前の問いを全体図で振り返る。
