## 05-01 IoT Hub の後ろに何をつなぐか

### このページの役割

前章までの D2C 送信・受信と制御に続き、IoT Hub が受け取ったメッセージを後続サービスへ配送するルーティングを導入する。IoT Hub を取り込み口として位置づける。

### 投影本文

**IoT Hub は取り込み口であり、保存・分析・可視化は後続サービスと組み合わせる。**

- デバイスは引き続き IoT Hub に送信し、後続サービスへの配送は IoT Hub 側で設定する。
- 配送条件には、メッセージ本文・メッセージプロパティ・Device Twin の情報を利用できる。
- 主な配送先: Azure Storage、Azure Event Hubs、Azure Service Bus、Azure Cosmos DB、Microsoft Fabric Eventstreams（プレビュー）。

**一つのメッセージは、条件に一致する複数の配送先へ送れる。1つの配送先だけに振り分ける仕組みではない。**（[ルーティングの概要と配送先](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-messages-d2c#routing-endpoints)）

### 図の構成

- 左に IoT Hub、右に主な配送先を縦に並べ、IoT Hub から各配送先へ分岐する矢印を描く。
- Fabric Eventstreams には「プレビュー」ラベルを付ける。
- 「同じメッセージが複数先へ」を、1本の入力から複数の分岐で表す。

### 講師ノート

- 目安: 2分。「温度テレメトリを受け取ったあと、すべて同じ処理に流すとは限らない」と切り出す。
- 例として「全データを Storage に保存し、温度28度以上は Service Bus にも送る」構成を口頭で示す。
- 次への接続: 「配送を設定するために、対象・条件・配送先の言葉を整理します」。

## 05-02 データソース・ルート・エンドポイント

### このページの役割

ルーティング設定で使う3つの用語を、決めることと今回の例で対応づける。データソースが「何を送ったか」で決まることも押さえる。

### 投影本文

**ルートは配送ルール、エンドポイントは配送先の設定。データソースは配送対象の種類を選ぶ。**

| 用語 | 決めること | 今回の例 |
| --- | --- | --- |
| データソース | 何を配送対象にするか | デバイスのテレメトリ |
| エンドポイント | どこへ送るか | Blob Storage のコンテナーを指す設定 |
| ルート | 対象・条件・配送先を結び付けるルール | 温度28度以上のテレメトリを保存先へ送る |

- データソースは関数名ではなく「何を送ったか」で決まる。`send_message()` の温度・湿度はデバイス テレメトリ メッセージ、Reported の更新はデバイス ツイン変更イベントになる。
- **エンドポイント名とストレージアカウント名は別で、同じ名前にする必要はない。** 例: エンドポイント `telemetry-storage` がアカウント `stiotdemo001` のコンテナー `telemetry` を参照する。

**設定は Portal メニュー「メッセージ ルーティング」で行い、エンドポイント登録はルート作成中にもできる。**（[Portal でのルートとエンドポイントの作成](https://learn.microsoft.com/ja-jp/azure/iot-hub/how-to-routing-portal?tabs=storage)、[ルーティングのデータソース](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-messages-d2c)）

### 図の構成

- 3行の用語表を上に置き、「決めること」と「今回の例」を同じ列で対比する。
- 下部に「データソース＝何を送ったか」を示す小さな対応（`send_message()`→テレメトリ、Reported 更新→Twin 変更）を配置する。

### 講師ノート

- 座学では上の対応を押さえ、その他のデータソース（C2D、Direct Method 応答は含まない）は紹介に留める。今回のデモではテレメトリを選ぶ。
- 配送先への認証・権限、ネットワーク要件による制約は第7章で扱うと予告する。
- 次への接続: 「では、どの配送先を選ぶかを目的から整理します」。

## 05-03 目的から配送先を選ぶ

### このページの役割

組み込みエンドポイントを起点に、配送先を目的で使い分ける。組み込みは読み取り口であり、長期保存は別の配送先が必要と示す。

### 投影本文

**配送先は、アプリでの受信・履歴保存・検索・ストリーム分析・業務処理という目的で選ぶ。**

| 配送先 | 主な目的 | 温度・湿度データでの利用例 |
| --- | --- | --- |
| 組み込みエンドポイント | アプリがメッセージを読み取る | IoT Explorer での受信確認、自作アプリでの温度判定 |
| Blob Storage / ADLS Gen2 | ファイルとして履歴を保存し後から分析 | 全測定データを残し後日まとめて集計 |
| Cosmos DB | DB に保存し条件を指定して取り出す | 特定デバイスの測定履歴を画面に表示 |
| Event Hubs | 大量の連続データをストリーム処理へ渡す | 多数デバイスの温度を継続的に集計・分析 |
| Service Bus | 業務処理へメッセージを渡す | 高温通知から保守チケットを作成 |

**組み込みエンドポイントは読み取り口で、保持期間は既定1日・最大7日。長期保存は別の配送先が必要。配送先は目的に応じて複数へ同時に送れる。**（[IoT Hub の配送先](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-endpoints#custom-endpoints-for-message-routing)、[組み込みエンドポイントと保持期間](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-messages-read-builtin)）

### 図の構成

- 5行の比較表を中央に置き、優劣ではなく目的で対比する。
- 組み込みエンドポイントの行に「保持: 既定1日・最大7日」の注記を添える。

### 講師ノート

- 目安: 2分30秒。Storage と Cosmos DB は「ファイルで残すか、DB で取り出すか」、Event Hubs と Service Bus は「連続する観測データか、業務メッセージか」で比較する。
- 「Event Hubs 互換」は Event Hubs 用 SDK で読める意味で、別リソースの作成は不要（Python は `azure-eventhub`）。
- 配送するだけで集計やチケット作成は完了しない。後続処理も設計する。
- 次への接続: 「同じデータを2経路へ同時に流す設計を見ます」。

## 05-04 ホットパスとコールドパスに同時配送する

### このページの役割

同じテレメトリを、低遅延で使うホットパスと、蓄積して後から使うコールドパスの両方へ配送できることを示す。分析処理は後続が担うと区別する。

### 投影本文

**同じテレメトリを、低遅延で活用するホットパスと、蓄積して後から分析するコールドパスの両方へ配送できる。**

| 経路 | 配送先と後続処理の例 | 温度・湿度データでの目的 |
| --- | --- | --- |
| ホットパス | IoT Hub → Event Hubs → ストリーム処理・通知 | 現在の温度を監視し、短い時間窓の集計や高温アラートに使う |
| コールドパス | IoT Hub → Blob Storage / ADLS Gen2 → バッチ分析 | 測定履歴を保存し、日次集計・傾向分析・機械学習用の準備に使う |

- 例: 2本の通常ルート `hot-telemetry`（条件 `true`）と `cold-archive`（条件 `true`）を有効にすると、デバイスは1回送信し IoT Hub が両方へ配送する。
- ホットパスを高温だけに絞るなら、条件を「温度28度以上」に変える（条件式の書き方は次ページ 05-05）。平均など通常値も使う集計では、必要なデータを落とさない条件を選ぶ。

**ホット／コールドは処理経路の設計上の呼び方で、IoT Hub の専用モードではない。Event Hubs に配送するだけで KPI 計算やアラートは完成しない。**（[ホットパスとコールドパスの考え方](https://learn.microsoft.com/ja-jp/azure/architecture/databases/guide/big-data-architectures)、[複数宛先への配送](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-messages-d2c#routing-endpoints)）

### 図の構成

- 左に IoT Hub、右上にホットパス（Event Hubs → ストリーム処理・通知）、右下にコールドパス（Storage → バッチ分析）を分岐で描く。
- IoT Hub が担当する配送先までと、その後の処理を線種や区切りで分ける。両ルートに `true` を表示する。

### 講師ノート

- 目安: 2分30秒。Day 01 のスライド全体は転載せず、D2C と後続の2経路に絞る。デモに Event Hubs や分析基盤の構築は追加しない。
- コールドパスは障害時の予備ではなく、通常時から両方へ流す例である。
- 次への接続: 「経路を高温だけに絞るときに使う本文条件を見ます」。

## 05-05 本文を使う条件で対象を絞る

### このページの役割

ルーティングクエリの評価規則を示し、`true` と `$body.temperature >= 28` の違い、配送されるのはメッセージ全体であることを説明する。

### 投影本文

**ルーティングクエリは各メッセージについて評価され、結果が `true` のメッセージがそのルートの配送対象になる。**

| メッセージ本文 | 条件 `true` | 条件 `$body.temperature >= 28` |
| --- | --- | --- |
| `{"temperature":25,"humidity":45}` | 対象 | 対象外 |
| `{"temperature":29,"humidity":45}` | 対象 | 対象 |

- 既定の `true` は「常に成立する条件式」で、選んだデータソースの全メッセージが対象になる。
- `$body.temperature` は本文の温度を参照するが、一致時に配送するのは湿度も含むメッセージ全体。SQL の `SELECT`（列抽出）ではなく `WHERE`（対象の絞り込み）に相当する。
- 本文の評価には、有効な JSON と、本文を JSON と示す `contentType = application/json`・`contentEncoding = utf-8` の指定が必要になる（これが無いと IoT Hub が本文を中身の見えない文字列として扱い、条件で温度を読めない）。

**評価単位は D2C メッセージ1件で、これは IoT Hub が評価する条件式であり、デバイス側 Python の分岐ではない。**（[メッセージ本文に基づくクエリ](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-routing-query-syntax#query-based-on-message-body)）

### 図の構成

- 2行2列の評価表を中央に置き、同じ本文に対する2つの条件の結果を対比する。
- 表の下に「配送されるのはメッセージ全体（湿度も含む）」を一文で添える。

### 講師ノート

- 目安: 2分。デバイスは JSON を送り、IoT Hub が条件を評価すると強調する。
- `contentType`・`contentEncoding` 未指定だと本文が Base64 になり、本文条件が評価しにくくなる点を補足する。
- 次への接続: 「保存先に選んだ Storage で、いつ・どう保存されるかを見ます」。

## 05-06 Storage にいつ、どう保存されるか

### このページの役割

Storage への保存はバッチ書き込みであり、送信直後の保存ではないこと、保存形式は IoT Hub 側で選ぶことを説明する。

### 投影本文

**IoT Hub は Storage へ一件ずつ即時保存せず、まとめて書き込む。バッチ頻度の時間経過か、チャンクサイズ到達の、どちらか先に満たした方で書き出す。**

| 設定 | 意味 | 設定範囲 |
| --- | --- | --- |
| バッチ頻度 | たまったデータを書き出す時間間隔 | 60〜720秒 |
| チャンクサイズ | 書き出しの基準となるデータ量 | 10〜500 MB |

- 少量の温度・湿度データでは主に時間条件で書き出される。送信直後に Blob が見えなくても、まずバッチ分の待ち時間を見込む。これは保存完了の厳密な時間保証ではない。
- 保存形式（JSON か Avro）は送信形式ではなく、Blob への保存形式。JSON では `contentType = application/json`・`contentEncoding = utf-8` を指定する。未指定だと本文が Base64 になる。
- **既存エンドポイントの保存形式は後から変更できない。** 変える場合は新しいエンドポイントを作り、ルートの参照先を切り替える。

（[Storage への一括書き込みと保存形式](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-endpoints#azure-storage-as-a-routing-endpoint)、[ストレージエンドポイントの設定仕様](https://learn.microsoft.com/ja-jp/azure/templates/microsoft.devices/2019-11-04/iothubs)）

### 図の構成

- 左にメッセージがたまる様子、中央に「時間経過 または サイズ到達」の分岐、右に Blob への書き出しを描く。
- 下部に JSON / Avro の一行比較（JSON は内容確認向き、Avro は対応ツール前提のコンパクト形式）を添える。

### 講師ノート

- 目安: 2分。「少量しか届かなくても、サイズがたまるまで無期限に待つわけではない」と説明する。
- 短い間隔・小さいサイズは小さなファイルを増やしやすい。本番は遅延許容度と後続処理の扱いやすさで調整する。
- ファイルアップロード機能はメッセージルーティングとは別で、本章では扱わない。
- 次への接続: 「配送経路を明示し、各宛先で到達を確認する方針を見ます」。

## 05-07 配送経路の明示と到達確認

### このページの役割

通常ルートとフォールバックの違いを示し、必要な配送経路は組み込みも含めて明示する方針と、各宛先での到達確認を説明する。

### 投影本文

**必要な配送経路は、組み込みエンドポイントも含めて通常ルートで明示し、フォールバックだけに依存しない。**

- フォールバックルートは、どのルート条件にも一致しないメッセージだけを組み込みエンドポイントへ送る仕組みで、配送先障害時の代替保存先ではない。
- カスタムルートを追加すると、一致したメッセージが IoT Explorer に表示されなくなる場合がある。組み込みエンドポイント（`events`）にも全件流すには、そこを配送先とする条件 `true` のルートを明示する。
- ルートは先に一致した一つだけではなく、条件に一致するすべての宛先が配送対象になる。

**送信側の成功ログだけで完了とせず、意図した各配送先で受信・保存を確認する。配送先の障害や遅延はメトリック・リソースログ・エンドポイントの正常性で別途監視する。**（[フォールバックルート](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-messages-d2c#fallback-route)、[ルーティングの監視とトラブルシューティング](https://learn.microsoft.com/ja-jp/azure/iot-hub/troubleshoot-message-routing)）

### 図の構成

- 上段に「明示ルート」: Storage 宛て（条件 `true`）と `events` 宛て（条件 `true`）へ同じメッセージが同時配送される図。
- 下段に「フォールバック」: どのルートにも一致しないメッセージだけが組み込みへ向かう図。両者を対比する。

### 講師ノート

- 目安: 2分。デモは IoT Explorer の受信を開始してから送信し、デバイス ID・送信時刻・本文を確認する。Storage 側はバッチ書き込みを待って同じメッセージを確認する。
- 「一方で見えたこと」を、もう一方への到達確認の代わりにしない。
- 次への接続: 「章の到達点を事例で確認します」。

## 05-08 理解度の確認
