## 03-01 デバイス・IoT Hub・バックエンドの役割

### このページの役割

前章で選んだ直接接続を拡大する。「IoT Hub が全部処理する」という理解を避け、以降の登録・認証・送受信の担当を固定する。

### 投影本文

**デバイスアプリがデータを送り、IoT Hub が通信を仲介し、バックエンド（デバイスの外でデータを使う側）がデータを利用する。**

| 主体 | 担当すること |
| --- | --- |
| デバイスアプリ | 測定値を作って送る。受け取った操作や設定変更を実行する |
| Azure IoT Hub | デバイスを認証し、デバイスとの通信と後続への配送を担う |
| バックエンドアプリ・ツール | テレメトリ（デバイスが送る測定値などのデータ）を読み、保存・業務処理を行う。デバイスへの操作を要求する |

IoT Hub は接続・通信の基盤であり、長期保存・分析・デバイス上の処理はアプリや後続サービスと組み合わせる（[IoT Hub の概要](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-concepts-and-iot-hub)、[デバイスとサービスの SDK](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-sdks)）。

**今回: 温度センサー役のローカル PC → IoT Hub → 受信ツール。**

### 図の構成

- 上部に横一列で「デバイスアプリ」「IoT Hub」「バックエンド」を配置し、表の担当をそれぞれの直下に置く。
- データの矢印は左から右。「温度・湿度を送信」「受信アプリが読み取り」とラベルを付ける。右側の線は読み取りによるデータの流れであり、Hubが無条件にアプリへプッシュする意味ではない。
- 左に「ローカル PC」、中央に「Azure」、右に「実行場所は任意」と明記する。バックエンドを必ずAzure上で動かす図にしない。
- 保存・分析は右端に薄い破線で追加し、「今回の受信確認とは別」と書く。操作の矢印は03-11で追加する。

### 講師ノート

- 目安: 1分30秒。バックエンドとは、デバイスの外でデータ利用や操作要求を行うアプリ側のことと説明する。
- 本講義では受信ツールもバックエンドの役割を担う。デバイス役と受信役が同じPC上でも、役割・資格情報は別になる。
- 問いかけ: 「温度を測るプログラムはどこにありますか」。答えはデバイス側。
- 次への接続: 「この3者が通信するまでに、クラウド側とデバイス側で何を準備するでしょうか」。

## 03-02 Hub 作成からデバイス接続までの手順

### このページの役割

「Azure上に登録がある」と「アプリが動いて通信している」を分け、接続できない場合にも確認箇所の見当が付くようにする。

### 投影本文

**Hub と Device ID を作っても、デバイスアプリが自動で接続するわけではない。**

| 段階 | 誰が何をするか | この段階で用意・確認できること |
| --- | --- | --- |
| 1. Hub 作成 | 管理者がAzureにIoT Hubを作る | 接続先のHub |
| 2. デバイス登録 | 登録担当がHubにIDと認証方式を登録する | そのHubで受け入れるデバイスの情報 |
| 3. 接続設定 | 開発・設定担当がアプリに接続先と資格情報を渡す | 接続に必要な設定 |
| 4. 接続 | デバイスアプリが起動し、認証を伴う接続を行う | 接続処理の結果 |
| 5. 送受信確認 | デバイスが送り、受信担当がツールで読む | 対象デバイスのメッセージ |

IDレジストリはデバイスIDと認証情報を管理する場所であり、登録しただけではアプリは動作しない（[ID レジストリ](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-identity-registry)）。

**今回は手動登録。多数台の自動プロビジョニングは第7章で扱う。**

### 図の構成

- 5段階を左から右へ並べ、1・2の上に「クラウド側の準備」、3に「アプリの準備」、4・5に「実行と確認」を置く。
- 各段階の下に表の「用意・確認できること」を配置する。完了マークが後続段階へ自動伝播する表現は使わない。
- 下部の確認例は「登録済み ≠ 接続中」。ポータルの状態欄だけを現在の接続証明として扱わない。

### 講師ノート

- 目安: 2分。担当名は説明上の役割であり、5人を配置する必須要件ではない。登録まで済んだ状態とアプリを起動した状態を図上で指し分ける。
- 本編の対象はデバイスSDKで接続する今回のアプリ。全プロトコルの接続の持ち方を一律に説明しない。
- 接続できない場合の入口は「登録先のHub、Device ID、資格情報、ネットワーク」。診断コマンドや切り分け手順は広げない。
- 次への接続: 「3段階目で渡すものは、Device IDだけで十分でしょうか」。

## 03-03 Device ID とデバイスの資格情報

### このページの役割

識別子と認証材料を具体的に分ける。方式名の暗記ではなく、接続文字列を公開してはいけない理由を説明する。

### 投影本文

**Device ID は名前。資格情報は、そのデバイスとして認証するために使う。**

| 要素 | 今回の説明例 | 意味 |
| --- | --- | --- |
| 接続先 | `iot-training-hub.azure-devices.net` | どのHubに接続するか |
| Device ID | `temp-sensor-01` | Hub内のどのデバイスか |
| 資格情報 | 対称キー、または証明書と対応する秘密鍵 | そのデバイスとして認証する材料 |

デバイス認証の入口は、**対称キーで生成する有効期限付きのSASトークン（Shared Access Signature: 一時的な署名付きの資格情報）**と**X.509形式のデジタル証明書**。IDを知っているだけでは認証できない（[SAS による認証](https://learn.microsoft.com/ja-jp/azure/iot-hub/authenticate-authorize-sas)、[X.509 による認証](https://learn.microsoft.com/ja-jp/azure/iot-hub/authenticate-authorize-x509)）。

今回の対称キー方式の接続文字列の形（説明用・接続不可）:

```text
HostName=iot-training-hub.azure-devices.net;
DeviceId=temp-sensor-01;
SharedAccessKey=<非表示>
```

**接続文字列はURLではなく、キーを含む秘密情報。画面・コード・ログに公開しない。**（[デバイスの SAS 資格情報](https://learn.microsoft.com/ja-jp/azure/iot-hub/authenticate-authorize-sas)）

### 図の構成

- 左に「Hub側: 登録済みのDevice IDと認証方式」、右に「アプリ側: 接続先・ID・資格情報」を置く。
- Device ID同士を細線で対応付け、その下に「IDの一致だけでなく資格情報を検証」と書く。
- 接続文字列は3つのフィールドが対応するように改行表示し、「実際は1行」と添える。実キーらしいランダム文字列は生成しない。
- 認証方式は本文の2方式だけを短く示す。証明書チェーンや発行手順の図は追加しない。

### 講師ノート

- 目安: 2分。接続文字列の例は対称キー方式専用。X.509でも同じ `SharedAccessKey` を使うとは説明しない。接続先・ID・キーを表と対応付けて確認する。
- 対称キーとSASトークンは同じものではない。SDKはキーを使ってSASトークンを生成する。期限・更新処理の詳細はここでは省く（[SAS トークンの生成](https://learn.microsoft.com/ja-jp/azure/iot-hub/authenticate-authorize-sas)）。
- 図の「Hub側の登録情報」にデバイスの秘密鍵は含めない。X.509の秘密鍵はデバイス側で保護し、証明書と対応する秘密鍵を持つことを認証で確認する（[X.509 による認証](https://learn.microsoft.com/ja-jp/azure/iot-hub/authenticate-authorize-x509)）。
- デバイス固有の資格情報を別デバイスへ使い回さない。秘密鍵・キーの保管や更新の設計は第7章へつなぐ（[セキュリティ推奨事項](https://learn.microsoft.com/ja-jp/azure/iot-hub/secure-azure-iot-hub#identity-and-access-management)）。
- 次への接続: 「デバイスを認証できることと、クラウド側から他のデバイスを操作してよいことは別です」。

## 03-04 認証・認可・通信保護は別の問い

### このページの役割

なりすまし、不正な操作、通信経路での漏えいという異なる問いを、3つの基礎概念に結び付ける。方式名の暗記より、3つが別々の問いであることを固定する。

### 投影本文

**誰として接続するか、何を許可するか、通信内容をどう守るかは別の問い。**

| 観点 | 確認する問い | 具体例 |
| --- | --- | --- |
| 認証 | 誰として接続するか | `temp-sensor-01` として資格情報を検証する |
| 認可・権限 | その主体に何を許すか | 自分のテレメトリ送信と、サービス側からの操作を分ける |
| 通信保護 | 経路上で内容を守れるか | TLSで通信を暗号化する |

認証・認可・通信保護は別々の問い。認証できても、許可される操作の範囲や通信経路の保護は別に決まる（[アクセス制御と権限](https://learn.microsoft.com/ja-jp/azure/iot-hub/authenticate-authorize-azure-ad)、[TLS サポート](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-tls-support)）。

**次ページで、この認証をデバイス側とサービスAPIに分けて具体化する。**

### 図の構成

- 中央に3行の比較表（認証 / 認可・権限 / 通信保護）を配置し、同じ観点を同じ行で対比する。優劣の順位にはしない。
- 3つを縦に並べ、「誰か」「何を許すか」「経路を守るか」と短いラベルを付ける。
- TLSは通信保護の行にとどめ、具体的な認証方式（SAS / X.509）とは混ぜない。方式名は次ページで扱う。

### 講師ノート

- 目安: 1分40秒。表の「誰か」「何を許すか」「通信を守るか」を順に具体例と対応付け、3つが独立した問いであることを強調する。
- 認証・認可・通信保護は重なりやすいが別物。認証が通れば何でもできる、という理解を正す。
- 具体的な方式名（SAS / X.509 / Entra ID / RBAC）は次ページで扱い、ここでは概念の区別に集中する。
- 次への接続: 「では、この認証を主体ごとにどの方式で行うかを見ます」。

## 03-05 認証方式: デバイス側とサービスAPI

### このページの役割

前ページの「認証」を主体別に具体化する。サービス側の認証をデバイスへ流用する誤解を防ぐ。

### 投影本文

**接続する主体で認証方式が違う。デバイス用とサービス側の資格情報は分ける。**

| 主体 | 主な認証方式 |
| --- | --- |
| デバイス | SAS（対称キー由来）または X.509 証明書 |
| デバイス管理・操作のサービスAPI | Entra IDで認証 + Azure RBACで権限付与、または共有アクセスポリシー（Hub側の権限設定）のSAS |

**Entra ID認証はデバイスAPIには使えない。** サービス側の方式をデバイスの接続にそのまま使わない（[SAS とアクセス権](https://learn.microsoft.com/ja-jp/azure/iot-hub/authenticate-authorize-sas)、[Microsoft Entra ID によるサービス API の認証](https://learn.microsoft.com/ja-jp/azure/iot-hub/authenticate-authorize-azure-ad)）。

**TLSを使っていても、キーの公開が安全になるわけではない。デバイス用とサービス側の資格情報を混在させない。**（[TLS サポート](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-tls-support)）

### 図の構成

- 「デバイス側 → Hub ← サービス側」の小図を中央に置く。左に「デバイス固有の資格情報（SAS / X.509）」、右に「サービス側の認証と権限（Entra ID + RBAC / 共有アクセスポリシーのSAS）」を記す。
- キーを横断共有する線は描かない。Entra IDの矢印はサービス側だけに付け、デバイス側へ伸ばさない。
- 表と小図で同じ方式名を二重に強調しない。

### 講師ノート

- 目安: 1分20秒。Microsoft Entra IDはバックエンドの認証主体を扱い、Azure RBACは役割に応じたアクセス権を割り当てる仕組みと説明する（[Entra ID と RBAC](https://learn.microsoft.com/ja-jp/azure/iot-hub/authenticate-authorize-azure-ad)）。
- APIはアプリがサービスの機能を呼び出す窓口。「サービス側」はデバイス管理・操作などのサービスAPIを指し、すべての受信ツールが両方式に対応する意味ではない。
- この表はデバイスAPIとサービスAPIの認証。Hubリソースを作成する管理操作は別の操作面であり、サービス用SASをHub作成の資格情報として示さない（[IoT Hub SDK の分類](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-sdks)）。
- 権限ロール名の一覧、TLSバージョン、脅威分類、証明書運用は説明しない。第7章で権限・保護・更新の具体的な設計へ進む。
- 次への接続: 「接続する主体と保護が分かったところで、どの通信方式を使うかを比べます」。

## 03-06 IoT Hub の通信プロトコルと選び分け

### このページの役割

認証・TLSの説明を受け、デバイスとHubの間で使う通信方式を比較する。名前の列挙ではなく、指示の受信方法、デバイスIDの多重化、ポートの違いを判断材料にする。SDKによる実装は次ページで扱う。

### 投影本文

**通信プロトコルはデータをやり取りする方式。デバイスの制約と受信方法に合わせて選ぶ。**

| 観点 | MQTT | AMQP | HTTPS |
| --- | --- | --- | --- |
| 主な選択場面 | 一般的なデバイスの直接接続 | 複数デバイスを集約するゲートウェイ | 他の方式を利用できないデバイス |
| クラウド→デバイスのメッセージ受信（C2D） | サーバーからプッシュ | サーバーからプッシュ | デバイスから定期的に問い合わせる（ポーリング） |
| 1つのTLS接続で扱うデバイスID | 1つ | 複数IDを多重化できる | 1つ |
| 送信先ポート | 8883 / WebSocket経由は443 | 5671 / WebSocket経由は443 | 443 |

IoT Hubのデバイス側通信を比較。C2Dメッセージを速やかに受け取る用途はMQTT / AMQPを選ぶ。操作機能全般の対応比較ではない（[対応プロトコル・選択基準・ポート](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-protocols)）。

**443番ポートを使う通信が、すべてHTTPS方式になるわけではない。** MQTT / AMQPはWebSocket経由でも利用できる（[WebSocketとポート番号](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-protocols#port-numbers)）。

**IoT HubのMQTT対応は機能が限定され、汎用MQTTブローカーと同じではない。**（[MQTTサポートの範囲](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-mqtt-connect-to-iot-hub)）

### 図の構成

- 中央に4行の比較表を配置し、同じ観点を同じ行で対比する。優劣のランキングにはしない。
- WebSocketはMQTT / AMQPのポート欄に併記し、独立した機能選択の列にはしない。
- 表の下に選択基準と2つの留保を通常の本文サイズで配置する。Learnへのリンクは同じスライド下端に残す。
- 対象はデバイス側の接続。受信バックエンドの読み取り口やサービスAPIを同じ比較表に混在させない。

### 講師ノート

- 目安: 2分。方式の定義と表の比較75秒、WebSocketとMQTTの留保30秒、SDKへの接続15秒。
- クラウドからデバイスへのメッセージをC2Dと呼ぶ。表の「メッセージ受信」はC2Dの説明であり、すべての操作機能がHTTPSで利用できるという意味ではない。Direct Methodなどの使い分けは第4章へ残す。

## 03-07 SDK の役割と用途別の使い分け

### このページの役割

SDKは実行する役割に合わせて選ぶ。D2Cはデバイスからクラウドへの通信（Device-to-Cloud）を指す（[IoT Hub SDK](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-sdks)、[D2C 読み取りの SDK](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-messages-read-builtin#sdk-samples)）。

## 03-09 D2C を読む組み込みエンドポイント

### このページの役割

IoT Hubと受信ツールの間にある読み取り口を可視化する。別のEvent Hubsリソースを必ず作るという誤解を防ぐ。

### 投影本文

**受信アプリは、IoT Hubが標準で用意する組み込みエンドポイントをEvent Hubs SDKで読む。**

- 組み込みエンドポイント `messages/events` は **Event Hubs互換**。別のEvent Hubsリソースの作成は不要（[組み込みエンドポイントの読み取り](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-messages-read-builtin)）。
- 受信アプリ側は **pull型**。SDKがオフセット位置から継続的に取得し、届いた分を受け取る（[Event Hubs のコンシューマー（プルモデル）](https://learn.microsoft.com/ja-jp/azure/event-hubs/event-hubs-features#event-consumers)）。
- 前提は **ルート未定義、またはフォールバックルートが有効**で、メッセージが組み込みエンドポイントに届く構成（変更時は第5章）（[フォールバックルート](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-messages-d2c#fallback-route)）。

組み込みエンドポイントは期限付きでメッセージを保持する読み取り口であり、長期保存用のDBではない。読み取りは共有アクセスキー方式で接続する（[組み込みエンドポイントの読み取り](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-messages-read-builtin)）。

### 図の構成

- 左にデバイス、中央に大きなIoT Hubの枠、右に受信アプリ・ツールを配置する。
- Hubの枠内に「組み込みエンドポイント messages/events（IoT Hubが標準提供）」を置く。デバイスの送信先に `messages/events` を直接指定する図にはしない。
- データの矢印は「デバイス → Hub → 組み込みエンドポイント → 受信アプリ」。最後の矢印に「Event Hubs SDKでpull（受信アプリが取得）」と明記する。
- 図上部に前提「ルート未定義、またはフォールバックルートが有効」、図下部に「Event Hubsリソースの追加は不要」。SDK名を独立したクラウドサービスの箱で描かない。
- 受信アプリの下に「読み取り権限を持つ共有アクセスポリシーの資格情報」と置く。デバイス側のキーとは別に描く。

### 講師ノート

- 目安: 2分30秒。エンドポイントとは、アプリが通信機能を使うための接続口。追加の1分で、図の読み取り経路を追い、受信側の資格情報と03-05のサービスAPI認証の違いを確認する。
- 受信は pull モデル。`receive()` を呼ぶと SDK が内部で継続的に pull し、届いたイベントを `on_event` に渡す（サーバープッシュではない）（[Event Hubs はプルモデル](https://learn.microsoft.com/ja-jp/azure/event-hubs/event-hubs-faq#what-protocols-i-can-use-to-send-and-receive-events)）。
- `messages/events` は組み込みエンドポイントの名前・パス。受信設定に必要な接続先情報をこの文字列だけで代替できるとは説明しない。
- 読み取りは共有アクセスキー方式のみで、`ServiceConnect` を持つ共有アクセスポリシーを使う。組み込みエンドポイントでは RBAC / Entra ID は使えず、Entra ID で読みたい場合はカスタム Event Hubs へルーティングする。デバイス用の接続文字列は使わない。資格情報の形式はSDK・ツールに合わせ、第6章で実接続を確認する（[サービスAPIの権限（組み込みは共有アクセスキー）](https://learn.microsoft.com/ja-jp/azure/iot-hub/authenticate-authorize-azure-ad#permissions-for-iot-hub-service-apis)、[組み込みエンドポイントへの接続](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-messages-read-builtin#connect-to-the-built-in-endpoint)）。
- パーティション、コンシューマーグループ、保持日数、チェックポイント、フォールバック条件は第5章の担当。
- 制作前提はフォールバックルートも有効のままにした初期構成。ルート未定義でも配送設定を無効にした構成に一般化しない。第5章の「必要な配送先を通常ルートで明示する」方針とは、対象とする構成段階が異なる（[既定の配送とフォールバック](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-messages-read-builtin)）。
- 次への接続: 「次に、送ったものと読み取ったものを並べて確認します」。

## 03-10 送信ログと受信データの照合

### このページの役割

送信処理の成功、受信確認、業務処理完了という3つの観測範囲を分ける。受信画面が空でも原因を一つに決め付けない姿勢を作る。

### 投影本文

**送信側の成功ログと、受信側に現れた送信元・本文を対応させて確認する。**

送信側の表示例（説明用）:

```text
Device connected to IoT Hub.
Sent telemetry: {'temperature': 25, 'humidity': 45}
```

**同じ値の繰り返しがあり得るため、値の一致だけでは1件を一意に識別した証明にはならない。1件を確実に識別・突き合わせるには次を使う:**

| 目的 | 使うもの |
| --- | --- |
| 送信元の特定 | `iothub-connection-device-id`（Hubがなりすまし防止で刻む送信元ID。本文中のIDは根拠にしない） |
| メッセージの識別 | `message-id`（`message.message_id`。デバイスが各メッセージに一意付与。重複検知の起点） |
| 時刻の基準 | 到着時刻（enqueuedTime）／デバイスが付ける送信時刻で並べる |

**送信ログや受信表示を確認しても、DB保存・後続の業務処理の完了は別に確認する。**（[メッセージの構造とシステムプロパティ](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-messages-construct)、[組み込みエンドポイントからの読み取り](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-messages-read-builtin)）

### 図の構成

- 左45%に送信ログ、右45%に受信表示の表。温度・湿度の値を細線で対応付け、送信元IDには別ラベルを付ける。
- 受信表示の脇に「一意識別に使う項目: iothub-connection-device-id / message-id」を小さく添える。値の一致だけを識別根拠に見せない。
- 下部に「送信処理の成功 / 受信側で確認 / 保存・業務処理完了」を横並びに置き、最後には「この画面では未確認」と記す。

### 講師ノート

- 目安: 3分。説明80秒、照合と一意識別の方法55秒、限界と切り分け45秒。
- ログの2行の間には `start` の操作がある。実装はその操作自体をこの形式でログ出力しないため、架空の実ログを補わない（[デモ実装](https://github.com/zukakosan/demo-azure-iot/blob/main/demo/01_iothub-send-tel.py)）。

- 受信表示が空なら、未送信・送信開始前・読み取り設定・配送経路などを順に疑う。「IoT Hubが落ちている」と即断しない。
- 次への接続: 「受信できた後に、センサーを操作したり履歴を保存したりする要求が加わります」。

## 03-12 Basic・Standard・Free の機能差

### このページの役割

| 今回確認する機能 | Basic | Standard | Free（評価用） |
| --- | --- | --- | --- |
| D2C・メッセージルーティング | 対応 | 対応 | 対応 |
| Direct Method・Device Twin・C2D | 非対応 | 対応 | 対応 |
