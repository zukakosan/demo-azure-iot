## 04-01 クラウドからデバイスへ働きかける3つの目的

### このページの役割

前章までの「デバイスからクラウドへ送る（D2C）」に対し、逆方向の「クラウドからデバイスへ働きかける」操作を導入する。手段の名前より先に、目的で使い分ける軸を置く。

### 投影本文

**クラウドからデバイスへ働きかける操作は、目的とオフライン時の要件で使い分ける。**

| 目的の例 | やりたいこと | 適した手段 |
| --- | --- | --- |
| 今すぐ操作したい | ファンを今止め、結果をその場で確認する | Direct Method |
| 設定を変えたい | 送信間隔を10秒に変え、その状態を保ちたい | Device Twin |
| 通知・依頼を届けたい | メンテナンス予定や診断ログ依頼を届ける | C2D メッセージ |

**「今やって結果を教えて」は Direct Method、「この状態にしておいて」は Device Twin、「この通知・依頼を届けて」は C2D。**（[通信方式の選択ガイド](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-c2d-guidance)）

### 図の構成

- 3つのシナリオカードを横並びにし、各カードに「目的」「例」「手段」を配置する。
- カードは同じ大きさだが、手段名を色分けして識別できるようにする。色だけに頼らずラベルも付ける。

### 講師ノート

- 目安: 2分。3つの日常的な例（今止める・設定を変える・通知する）を先に出し、手段名は後で対応させる。
- ここでは仕組みの詳細に入らず、「目的で選ぶ」という軸だけを共有する。
- 次への接続: 「この3つを、用途とオフライン時の挙動で比べます」。

## 04-02 Direct Method・Device Twin・C2D の使い分け

### このページの役割

3手段を同じ観点で比較し、オフライン時の挙動という判断軸を加える。

### 投影本文

**同じ「クラウド→デバイス」でも、要求の形とオフライン時の扱いが異なる。**

| 方法 | 主な用途 | オフライン時の扱い |
| --- | --- | --- |
| Direct Method | 即時操作し、その場で応答を確認する | 接続待ち時間内に接続できなければ失敗。後日配送用のキューには保持しない |
| Device Twin の Desired Properties | デバイスを最終的に期待する構成へ合わせる | 期待値が保持され、再接続時に適用できる |
| C2D メッセージ | デバイスへの一方向の通知・依頼 | 一定期間キューに保持される（既定 TTL 1時間、最大2日） |

**継続的に維持したい構成は Twin に期待値として保持し、個別の通知・依頼は C2D で届ける。オフラインで届けたいからといって、すべてを C2D にはしない。**（[通信方式の保持特性](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-c2d-guidance#comparison-of-cloud-to-device-communication-options)、[C2D の保持と TTL](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-messages-c2d)）

### 図の構成

- 3行の比較表を中央に配置し、同じ観点を同じ列で対比する。優劣のランキングにしない。
- オフライン時の列を強調し、後日配送用キューを持つのは C2D だけであることを示す。

### 講師ノート

- 目安: 2分30秒。用途とオフライン挙動を対で読む。
- Desired の「保持」と C2D の「保持」は別。Desired は期待構成の保持、C2D はメッセージのキュー保持であり有効期限がある。
- 次への接続: 「C2D でも開始・停止は作れます。それでも Direct Method を使う理由を見ます」。

## 04-03 C2D でも制御できるが、Direct Method と何が違うか

### このページの役割

「C2D は通知用途」という理解が、制御できないという誤解にならないようにする。違いは制御可否ではなく、要求・応答と未接続時の扱いにあると示す。

### 投影本文

**C2D でも開始・停止は実装できる。違いは制御できるかどうかではなく、要求・応答と未接続時の扱いにある。**

C2D で `{"action": "start"}` を送り、受信ハンドラで送信を開始すれば、Direct Method と同じ処理を実装できる。

| 比較 | Direct Method | C2D メッセージ |
| --- | --- | --- |
| 基本の形 | 要求と応答 | 一方向のメッセージ配送 |
| 実行結果の確認 | 同じ要求への応答としてステータス・本文を返せる | 結果が必要なら、返送と要求の対応付けをアプリ側で実装する |
| 未接続時の扱い | 長期キューには保持しない | 有効期限内はキューに保持できる |
| 選ぶときの意図 | 「今、開始して。結果を教えて」 | 「これを届けて。受信したら処理して」 |

**遅れて届いた操作を実行してよいかも選定基準になる。停止中に届いた「開始」を再接続後に実行すると、意図と異なる場合がある。**（[通信方法の比較](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-c2d-guidance#comparison-of-cloud-to-device-communication-options)、[C2D の保持と有効期限](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-messages-c2d)）

### 図の構成

- 4行の対比表を中央に置き、Direct Method と C2D を左右で比較する。
- 下部に「遅れて届いた操作を実行してよいか」を判断軸として強調する。

### 講師ノート

- 目安: 2分。冒頭で「C2D でも制御は作れる」と明言し、通知専用という誤解を解く。
- C2D の配送フィードバックは Direct Method のアプリ応答とは別で、送信開始処理の成功までは自動報告しない。結果確認を作るなら要求 ID と D2C の返送で対応付ける。
- 次への接続: 「では、何を確認できたら成功と言えるかを整理します」。

## 04-04 送信成功・応答・実行成功は同じではない

### このページの役割

クラウドの送信成功、デバイスの応答、アプリの実行完了を分ける。応答タイムアウトや送信成功の解釈を誤らないようにする。

### 投影本文

**クラウドへの送信成功、デバイスからの応答、アプリの実行完了は別の事実。**

| 観点 | Direct Method | C2D メッセージ |
| --- | --- | --- |
| クラウド側が確認するもの | 要求に対するデバイスの応答 | まずは IoT Hub への送信・キューへの受け付け |
| 未接続時 | 接続待ち時間内に接続できなければ失敗 | キューに保持し、有効期限内の受信を待てる |
| 結果の解釈 | 応答タイムアウトでも、未実行とは限らない | 送信成功でも、受信・処理成功とは限らない |

**Direct Method の応答タイムアウトは「実行されなかった」ではなく「期限内に結果を確認できなかった」。C2D の送信成功は「デバイスが処理した」ではなく「IoT Hub が受け付けた」。**（[Direct Method の応答仕様](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-direct-methods#invoke-a-direct-method-from-a-back-end-app)、[C2D のキューと配送](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-messages-c2d)）

### 図の構成

- 上部を Direct Method / C2D の比較表、下部を「クラウド送信 → デバイス受信 → アプリ処理完了」の3段階に分ける。
- 各段階に「ここまで確認できた／ここは未確認」を対応させ、成功の範囲を段階で示す。

### 講師ノート

- 目安: 2分30秒。エラーコードの詳細（HTTP 404 / 504、応答本文の status）は質疑用に留める。
- デバイスが応答本文の status に設定する値と、IoT Hub の HTTP ステータスは別。前者はデバイスが応答を返した結果である。
- 結果不明時の再試行設計は第7章の信頼性へつなぐ。
- 次への接続: 「デバイスが停止していた場合、C2D はどう扱われるかを見ます」。

## 04-05 C2D の保持と再接続後の受信

### このページの役割

C2D の「一定期間キューに保持」を具体化する。保持するのはデバイスではなく IoT Hub であること、TTL を過ぎると受信できないことを示す。

### 投影本文

**C2D メッセージは IoT Hub のデバイス別キューに保持される。有効期限内に同じ Device ID で再接続すれば受信できる。**

- 保持するのは、停止中のデバイスアプリではなく IoT Hub のキュー。
- 既定 TTL は1時間、設定可能な最大値は2日。無期限の保存ではない。
- 「SDK が受信した結果、登録済みハンドラが呼ばれる」。Python SDK の登録先は `on_message_received`。

**配送の確認と、アプリ固有の処理の成功は別。結果が必要なら、返送と要求の対応付けをアプリ側で設計する。**（[C2D メッセージの保持と設定](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-messages-c2d)、[Python の C2D 受信ハンドラ](https://learn.microsoft.com/ja-jp/azure/iot-hub/how-to-cloud-to-device-messaging?pivots=programming-language-python#create-a-device-application)）

### 図の構成

- クラウド送信ツール、IoT Hub のデバイス別キュー、デバイスアプリ、C2D ハンドラの4者でシーケンスを描く。
- 「有効期限内に再接続」と「期限切れ」の2分岐を示す。期限切れ側は受信できないことを明記する。
- 編集可能な図形・線・テキストで再構成し、Mermaid の描画画像を貼り付けない。

### 講師ノート

- 目安: 2分。デバイス停止中に送った C2D が、再接続後に配送される流れを追う。
- 期限切れの分岐では「後から再接続しても受信できない」を強調する。
- 次への接続: 「継続的な設定は、キューではなく Device Twin で保持します」。

## 04-06 Device Twin の構造（Desired・Reported・Tags）

### このページの役割

Device Twin の3要素を役割で区別する。Desired と Reported を混同しないための基礎を置く。

### 投影本文

**Device Twin は、期待する構成・報告された状態・分類情報を保持する。**

| 要素 | 誰が書くか | 内容 |
| --- | --- | --- |
| Desired Properties | クラウド側 | 期待する構成。例: 送信間隔を5分に変更する |
| Reported Properties | デバイス側 | 報告する現在の構成・状態。例: 送信間隔を5分へ変更済みと報告する |
| Tags | クラウド側 | 拠点・機種・展開グループなどの分類情報。デバイスには配送しない |

**Desired は期待状態、Reported は実状態、Tags はクラウド側の分類情報。Desired の更新だけでは適用完了ではない。**（[Device Twin の構造](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-device-twins)）

### 図の構成

- Twin を左右に分割し、左に「デバイスが書く Reported」、右に「クラウドが書く Desired・Tags」を配置する。他章と同じくデバイスを左に揃える。
- Tags はデバイスへ配送されないことを図中で明示する。

### 講師ノート

- 目安: 1分30秒。Desired と Reported が自動的に同じ値になるものではないと強調する。
- Tags はクラウド側の分類用で、デバイスの動作設定ではない。
- 次への接続: 「Desired を変えてから、実際に適用されるまでの流れを見ます」。

## 04-07 Desired と Reported の状態同期

### このページの役割

Desired の更新から適用、Reported の報告までを時系列で示し、適用完了の確認方法を説明する。

### 投影本文

**Desired の更新は、デバイスへの適用完了を意味しない。実際の適用は Reported で確認する。**

1. クラウド側が Desired Properties を更新する（例: 送信間隔を5分に）。
2. デバイスが変更を受け取り、送信間隔へ適用する。
3. デバイスが適用結果を Reported Properties へ書き戻す。
4. クラウド側が Reported を読み、期待値と一致したか確認する。

**Desired と Reported は非同期。更新した事実と、各デバイスでの適用成功は分けて確認する。**（[Device Twin による状態同期](https://learn.microsoft.com/ja-jp/azure/iot-hub/iot-hub-devguide-device-twins#back-end-operations)）

### 図の構成

- Desired 更新 → デバイス適用 → Reported 更新 → クラウド確認の4段階タイムラインを描く。
- Desired 更新直後は Reported が未更新であることを、時間差として明示する。

### 講師ノート

- 目安: 1分30秒。共通ユースケースの送信間隔変更を例に、4段階を追う。
- 一括で Desired を送った事実と、各デバイスでの適用成功を区別する。段階展開・結果確認は第7章へつなぐ。
- 次への接続: 「ここまでの3手段を、事例で確認します」。

## 04-08 理解度の確認

### このページの役割

機能名の復唱ではなく、短い事例で章の到達点を確認する。答えは講師ノートに置く。

### 投影本文

**次の場面で、どの手段を選ぶか説明してください。**

1. ファンを今すぐ停止し、結果を確認したい。
2. オフライン中のデバイスにも、送信間隔の変更を届けて保ちたい。
3. 「再接続後に診断ログを送ってほしい」と「再接続後も送信間隔を10秒に保ってほしい」を選び分ける。
4. Direct Method の応答タイムアウトと C2D の送信成功から、それぞれ何が分かり、何が分からないか。

**次章: IoT Hub が受け取った D2C を、条件に応じて後続サービスへ配送するルーティングを扱う。**

### 図の構成

- 4つの問いを縦に配置し、答えは投影しない。
- 下部に Direct Method・Device Twin・C2D の小さな対応図を置き、指さして回答できるようにする。

### 講師ノート

- 目安: 1分。回答を考える時間を取り、口頭で答え合わせする。
- 問1: Direct Method（即時操作＋応答）。問2: Device Twin の Desired（オフラインでも期待値を保持）。
- 問3: 診断ログ依頼は C2D、送信間隔の維持は Device Twin。問4: タイムアウトは「結果未確認」、送信成功は「Hub が受け付け」まで。
- 次章への接続: 「受信できたデータを、どこへどう配送するかを見ます」。
