# 2. 接続パターンとサービスの選択 - スライド案

## Slide 1: 接続パターンは要件から決める

### スライドの目的
IoT サービスの選択を、サービス名ではなく現場要件から考える姿勢に切り替える。

### キーメッセージ
最初に決めるのは「どのサービスを使うか」ではなく、「デバイスや設備をどこで、どう接続する必要があるか」。

### スライド本文案
**接続パターンを決める主な問い**

- デバイスはインターネットへ直接接続できるか
- 現場側でプロトコル変換が必要か
- 低遅延処理やオフライン動作が必要か
- 複数拠点や設備ごとに接続条件が違うか
- データをどこで前処理し、どこへ送るか

**判断の流れ**

要件 → 接続パターン → Azure サービス

### レイアウト / ビジュアル案
- 左側: 「現場要件」のカードを 5 つ配置
- 右側: 「クラウド接続」「エッジ接続」「ハイブリッド」へ分岐するフロー図
- 下部に小さく「サービス名からではなく、要件から選ぶ」と強調

### 話す補足
ここでは IoT Hub と Azure IoT Operations をどちらが新しいか、どちらが上位かで比較しない。デバイスの接続条件、現場ネットワーク、運用要件によって適した接続パターンが変わる、という前提を置く。

---

## Slide 2: クラウド接続パターン

### スライドの目的
IoT Hub が中心になるクラウド直接接続の構成を理解する。

### キーメッセージ
デバイスがクラウドへ直接接続でき、クラウド側で一元管理したい場合は Azure IoT Hub が中心になる。

### スライド本文案
**向いているシナリオ**

- デバイスが MQTT、AMQP、HTTPS などでクラウドへ接続できる
- デバイスが地理的に分散している
- クラウド側でデバイス ID、認証、テレメトリ、状態を一元管理したい
- 現場側に複雑なプロトコル変換や低遅延処理の要件が少ない

**中心となるサービス**

Azure IoT Hub

### レイアウト / ビジュアル案
- 左側: 複数の温度センサーやデバイスのアイコン
- 中央: インターネットまたはネットワーク経由の矢印
- 右側: Azure IoT Hub の大きなカード
- IoT Hub から後続サービスへ薄い矢印を出し、詳細は次章以降で扱うことを示す

### 話す補足
クラウド接続パターンでは、IoT Hub がデバイス接続の入口になる。IoT Hub はデバイス単位の ID と資格情報を持ち、D2C テレメトリや C2D、Device Twin などの機能を提供する。保存や分析は IoT Hub の後ろにつなぐサービスが担当する。

## Slide 3: エッジ接続パターン

### スライドの目的
Azure IoT Operations が中心になるエッジ接続の考え方を理解する。

### キーメッセージ
産業プロトコル、低遅延、オフライン、閉域網などの現場要件が強い場合は、エッジで受けてクラウドへ連携する構成を検討する。

### スライド本文案
**向いているシナリオ**

- OPC UA などの産業プロトコルに対応した設備を接続したい
- 現場でデータの収集、変換、フィルタリングを行いたい
- クラウド接続が不安定、または常時接続できない
- 現場で低遅延な判断や制御が必要
- 工場や拠点単位で設備を管理したい

**中心となるサービス**

Azure IoT Operations

### レイアウト / ビジュアル案
- 左側: 工場設備、PLC、OPC UA 対応機器のアイコン
- 中央: エッジ環境の枠を置き、Azure IoT Operations を配置
- 右側: Azure / Fabric / IoT Hub などクラウド側サービスへ連携する矢印
- エッジ枠内に「収集」「変換」「フィルタリング」「クラウド連携」のラベル

### 話す補足
Azure IoT Operations は、現場の産業機器やエッジ要件を扱うための選択肢として説明する。IoT Hub の単純な置き換えではなく、現場側で何を受け、何を加工し、何をクラウドへ送るかを設計するためのサービス群として捉える。

---

## Slide 4: ハイブリッドと選択基準

### スライドの目的
現実の IoT 構成ではクラウド接続とエッジ接続が混在し得ることを示し、判断基準を整理する。

### キーメッセージ
1 つのシステムでも、拠点・設備・ネットワーク要件ごとに接続パターンを使い分ける。

### スライド本文案
| 要件 | 主な選択肢 |
| --- | --- |
| デバイスをクラウドへ直接接続できる | Azure IoT Hub |
| OPC UA などのプロトコル変換が必要 | Azure IoT Operations |
| 現場で低遅延処理やオフライン動作が必要 | Azure IoT Operations |
| クラウド接続とエッジ接続が混在する | ハイブリッド |
| デバイスや設備を Azure リソースとして管理したい | Azure Device Registry |
| データを蓄積・分析・可視化したい | Microsoft Fabric などの後続サービス |

### レイアウト / ビジュアル案
- 上部: 「クラウド接続」「エッジ接続」「ハイブリッド」の 3 つのカード
- 下部: 選択基準の比較表
- ハイブリッドカードでは、直接 IoT Hub へ接続するデバイスと、エッジ経由でクラウド連携する設備を同じ図に入れる

### 話す補足
サービス選択は二択ではない。たとえば、簡易センサーは IoT Hub へ直接接続し、工場内の既存設備は Azure IoT Operations 経由で接続する、という構成もあり得る。重要なのは、デバイスや設備の条件ごとに接続方式を決め、後続の保存・分析・可視化まで含めて全体を設計すること。

### 理解度確認
- デバイスがインターネットへ直接接続できる場合、中心になるサービスは何か
- OPC UA 対応設備を接続したい場合、どのサービスを検討するか
- 1 つの IoT システムでクラウド接続とエッジ接続が混在する理由は何か
