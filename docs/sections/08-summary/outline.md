# 8. まとめ

## この章の目的
ワークショップ全体で扱った設計判断を短く振り返り、IoT Hub を使い始める際に何を考えるべきかを定着させる。

## 聞き手に持ち帰ってほしいこと
- IoT Hub はクラウド接続パターンにおけるデバイス接続とメッセージングの中心である
- D2C、Direct Method、Device Twin、C2D メッセージは目的に応じて使い分ける
- 本番化では、デバイスから後続サービスまでをエンドツーエンドで設計する

## 扱う内容
- Azure IoT では、要件に応じてクラウド接続とエッジ接続を選択する
- IoT Hub はクラウド接続パターンの中心となるサービス
- D2C、Direct Method、Device Twin、C2D メッセージは目的に応じて使い分ける
- IoT Hub と後続の保存・分析サービスの役割を分ける
- 非機能要件は Well-Architected Framework の 5 つの柱で測定可能に定義する
- 本番化ではデバイスの製造から廃棄までと、エンドツーエンドの責任範囲を設計する

## 話す流れ
1. 共通ユースケースの流れに戻り、どの章で何を扱ったかを振り返る
2. IoT Hub の担当範囲と後続サービスの担当範囲を再確認する
3. 本番化では機能要件だけでなく、セキュリティ、信頼性、性能、運用、コストを同時に考えることを強調する

## 強調するポイント
- IoT Hub は万能なデータ基盤ではなく、デバイス接続とメッセージングの基盤である
- Device Twin は状態同期、Direct Method は即時操作、D2C はテレメトリ送信に使う
- 本番化ではデバイス、ネットワーク、クラウド、運用の責任分界を明確にする

## よくある誤解
- IoT Hub を作れば IoT ソリューション全体が完成する
- デモで動いた構成をそのまま本番にすればよい
- 非機能要件は後から考えればよい

## 理解度確認
- IoT Hub が担当する範囲と、担当しない範囲は何か
- 送信間隔の変更を扱う場合、なぜ Device Twin が適しているか
- 本番移行前に未定義だとリスクが高い項目は何か

## 付録: L200 の設計観点
本編では概要にとどめ、必要に応じて追加説明する。

- メッセージに時刻、スキーマバージョン、イベント ID を含める
- 受信側で重複、遅延、順序変更を考慮する
- IoT Hub への送信成功と後続の業務処理完了を区別する
- Device Twin の Desired と Reported を使って適用状況を管理する
- ルーティング先のスループット、保持期間、障害時の監視を設計する
- 資格情報のローテーションと失効手順を準備する
