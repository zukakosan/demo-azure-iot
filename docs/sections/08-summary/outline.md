# 8. まとめ

## この章の目的
ワークショップ全体で扱った設計判断を短く振り返り、IoT Hub を使い始める際に何を考えるべきかを定着させる。

## 聞き手に持ち帰ってほしいこと
- 接続パターンは通信方式、ネットワーク、処理場所の要件から選び、クラウド直接接続では IoT Hub がデバイス接続とメッセージングを担う
- デバイス ID の登録、デバイス固有の資格情報、アプリの接続は別の段階として確認する
- D2C、Direct Method、Device Twin、C2D メッセージは目的とオフライン時の要件に応じて使い分ける
- 本番化では、資格情報のライフサイクルとプロビジョニング、後続処理までの到達確認、測定可能な非機能要件を設計する

## 扱う内容
- Azure IoT では、要件に応じてクラウド接続とエッジ接続を選択する
- IoT Hub、デバイスアプリ、バックエンドの役割を分け、登録済みと接続中を区別する
- D2C、Direct Method、Device Twin、C2D メッセージは、通信の目的、保持、確認できる結果に応じて使い分ける
- IoT Hub は取り込みと配送を担い、保存・分析・業務処理は後続サービスが担う
- 必要な配送経路を明示し、送信成功と各配送先・業務処理への到達を分けて確認する
- 非機能要件は Well-Architected Framework の 5 つの柱を使い、目標値、判断基準、責任者、確認方法まで定義する
- 本番化では、デバイスの製造から廃棄までの資格情報管理、DPS によるプロビジョニング、再接続・再プロビジョニング、エンドツーエンドの責任範囲を設計する

## 話す流れ
1. 共通ユースケースに戻り、接続方式の選択、登録・認証・接続、送受信、制御・状態同期、後続配送、デモ確認を一つの流れで振り返る
2. D2C、Direct Method、Device Twin、C2D の目的と、各段階で確認できる結果を整理する
3. IoT Hub の担当範囲と後続サービスの担当範囲を再確認する
4. 本番化では、資格情報とプロビジョニングのライフサイクル、測定可能な非機能要件、エンドツーエンドの監視と責任者を決めることを強調する

## 図・デモで見せるもの
- 冒頭で使った全体アーキテクチャ図を再掲する
- 各コンポーネントに、接続方式の選択、登録・資格情報・接続、送受信・制御、ルーティング、到達確認のラベルを重ねたまとめ図
- 4つの通信・状態同期機能を、目的と確認できる結果で比較する表

## 強調するポイント
- IoT Hub は万能なデータ基盤ではなく、デバイス接続とメッセージングの基盤である
- デバイス ID の登録だけでは接続できず、デバイス固有の資格情報とアプリの接続処理が必要である
- D2C はテレメトリ送信、Direct Method は即時操作、Device Twin は状態同期、C2D は通知・依頼に使う
- 送信成功、デバイスでの実行・適用、配送先への到達、業務処理完了は同じではない
- 本番化ではデバイス、ネットワーク、DPS・IoT Hub、配送先、業務処理、運用の責任分界を明確にする

## よくある誤解
- IoT Hub を作れば IoT ソリューション全体が完成する
- デバイス ID を登録すれば、デバイスアプリが自動的に接続する
- IoT Hub への送信成功を確認すれば、保存や業務処理まで完了している
- デモで動いた構成をそのまま本番にすればよい
- 非機能要件は後から考えればよい

## 理解度確認
- IoT Hub が担当する範囲と、担当しない範囲は何か
- Hub に Device ID を登録した後、デバイスアプリの接続に必要なものは何か
- 即時停止、送信間隔の変更、再接続後に届ける通知には、それぞれどの機能を選ぶか
- IoT Hub への送信成功後、後続の業務処理完了までに何を確認する必要があるか
- 多数デバイスの本番運用へ進む前に、資格情報、DPS、容量、監視、責任者について何を決める必要があるか

## 付録: L200 の設計観点
本編では概要にとどめ、必要に応じて追加説明する。

- メッセージに時刻、スキーマバージョン、イベント ID を含める
- 受信側で重複、遅延、順序変更を考慮する
- IoT Hub への送信成功と後続の業務処理完了を区別する
- Device Twin の Desired と Reported を使って適用状況を管理する
- ルーティング先のスループット、保持期間、障害時の監視を設計する
- 資格情報のローテーションと失効手順を、製造・設置・運用・交換・廃棄の各段階で準備する
- DPS の登録集中を避けるため、時間差登録、バックオフ、ジッター、再接続と再プロビジョニングの判断条件を設計する
